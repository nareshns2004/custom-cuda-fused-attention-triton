# Design decisions

Read this before changing `kernels/`. Decisions 1–7 apply to the fused attention kernel, which
is being built in the disaggregated inference engine repo; they're recorded here because this
lab is where the groundwork (tests, tolerances, benchmarking discipline) is set.

| # | Decision | Alternative rejected | Cost accepted |
|---|----------|----------------------|---------------|
| 1 | Triton for attention | CUDA / CUTLASS (CuTe) | Less control over Hopper features (WGMMA, TMA, warp specialisation); will trail FlashAttention-3 on H100 |
| 2 | Forward only (prefill + decode) | Forward + backward | Can't be used for training; backward is future work |
| 3 | FP16/BF16 in, FP32 accumulate and softmax statistics | FP32 everywhere | Must state tolerances; FP32 matches nobody's production path |
| 4 | Autotune block sizes, warps and stages per shape | Fixed config | Compile time on first call |
| 5 | Separate decode kernel with split-K | Reuse the prefill kernel for decode | Two kernels to maintain; decode needs split-K to fill the GPU |
| 6 | Paged KV layout identical to the inference engine's transfer layout | Contiguous KV per sequence | Gather overhead in the kernel; the RDMA path moves blocks without repacking |
| 7 | All numbers generated by `benchmarks/` and stamped with GPU, driver, CUDA, Triton and PyTorch versions | Hand-written tables | Slower to publish; trustworthy |

## Learning-set decisions (this repo)

- **Triton kernels honour arbitrary strides.** Every launcher passes `tensor.stride(...)`;
  no kernel assumes contiguity. (Audit C2, C13 were both stride bugs.)
- **FP32 matmul uses IEEE precision by default** (`allow_tf32=False`), matching
  `torch.matmul`'s default. TF32 is opt-in. (Audit C9.)
- **CUDA kernels stay simple baselines.** They exist to show what Triton hides (shared memory,
  barriers, warp shuffles), not to compete with cuBLAS.
- **Tolerances live in one place**, `tests/tolerances.py`.

## Trade-offs to be ready to discuss

1. **Block size vs occupancy.** Larger tiles mean more reuse but more shared memory and
   registers, so fewer concurrent blocks. Autotuning picks the point per shape and GPU.
2. **Numerical stability vs speed.** Online softmax needs the max subtraction and rescaling;
   `exp2` with a pre-scaled `log2(e)` keeps stability and is faster.
3. **Split count in decode.** More splits fill the GPU at small batch but add a reduction pass;
   choose by batch × heads vs SM count.
4. **Generality vs performance.** Arbitrary strides, ragged lengths and GQA add index math;
   specialise with `tl.constexpr` where possible.
